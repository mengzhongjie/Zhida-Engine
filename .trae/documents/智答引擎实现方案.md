# 智答引擎（ZhiDa Engine）完整实现方案

---

## 一、项目概述

### 背景

智答引擎是一个基于 RAG（检索增强生成）架构的**个人 AI 知识助手**，以 Windows 桌面应用形式分发，接入微信群、QQ 群。核心差异在于**实时持续从聊天中学习**：

- 文档知识：上传 PDF/Excel/Word 构建基础知识库
- 实时学习：持续监听指定群/指定联系人的聊天，自动提取 Q&A 知识
- 持续进化：无需手动导入，知识随聊天自动增长
- Windows 原生应用：.exe 安装包，双击安装，开箱即用

### 目标用户

- **个人用户**：需要管理个人知识、自动回复群聊问题的个人
- **小团队/社群运营者**：需要沉淀群聊知识、减少重复回答的社群管理者
- **电商客服**：需要从客服聊天记录中自动提取 FAQ 的电商从业者
- **技术爱好者**：对本地 AI 部署感兴趣、注重数据隐私的技术用户

### 价值主张

- **零门槛部署**：下载 .exe → 双击安装 → 桌面快捷方式 → 开箱即用，无需 Docker/Python/数据库配置
- **数据不出机器**：全链路本地部署，知识库、聊天记录、向量数据全部存储在用户本地
- **持续进化**：不同于传统"上传文档 → 问答"的静态知识库，机器人从群聊中持续学习，知识自动增长
- **成本可控**：支持本地 Ollama 模型，LLM 调用可完全免费；云端 API 月成本约 100-300 元

### 要解决的核心问题

- 群聊/私聊中重复问题反复回答，人力成本高
- 大模型直接回答容易编造信息（幻觉），聊天场景不敢用
- 群内高手回答过的知识无法沉淀，随聊天流失
- 知识分散在文档和聊天记录中，没有统一管理和利用的渠道
- 现有方案部署复杂，个人用户无法快速上手

## 二、技术栈

| 层级 | 技术选型 | 选型理由 |
|------|---------|---------|
| **后端框架** | Python + FastAPI | AI/ML 生态最强（LangChain/LlamaIndex），RAG 系统唯一合理选择 |
| **打包分发** | PyInstaller → 单个 .exe | 将 Python + 所有依赖 + 前端静态文件打包为 Windows 原生可执行文件 |
| **安装包** | NSIS / Inno Setup | 制作标准 Windows 安装向导，双击安装，桌面快捷方式 |
| **RAG 编排** | LangChain + LlamaIndex 双引擎 | LangChain 管 Agent/Chain，LlamaIndex 管索引/检索 |
| **异步任务** | Python asyncio + 内置线程池 | 单用户桌面应用，无需 Celery 等重量级消息队列 |
| **业务数据库** | SQLite（嵌入式） | 零配置、零维护，数据存储在用户本地目录，单用户场景完全够用 |
| **缓存层** | diskcache（SQLite 后端） | 嵌入式缓存，无需单独 Redis 进程，支持持久化 + TTL |
| **向量数据库** | ChromaDB（嵌入式模式） | Python 原生，零依赖，数据随应用存储在本地 |
| **LLM 接入** | LiteLLM 统一网关 + Ollama 本地模型 | 兼容 OpenAI API + 100+ 提供商，支持本地模型 |
| **推荐模型** | DeepSeek V4-Pro / 通义千问 Qwen3.7 Max（云端）<br>Qwen3:14B / DeepSeek-R2（本地 Ollama） | 用户可在设置页自由切换 |
| **Embedding** | BAAI/bge-large-zh-v1.5（本地）<br>阿里云 DashScope（云端可选） | 中文嵌入 SOTA，本地运行免费用 |
| **管理后台前端** | React 18 + Ant Design 5 + TypeScript | 中文生态成熟，表格/表单丰富；嵌入 PyWebView 原生窗口 |
| **桌面窗口** | PyWebView（Windows WebView2） | 将 React 前端嵌入原生 Windows 窗口，无需浏览器 |
| **部署** | Windows .exe 安装包 | 双击安装 → 桌面快捷方式 → 原生窗口启动 |

### 为什么选 SQLite 而不是 PostgreSQL？

| 对比 | PostgreSQL | SQLite |
|------|-----------|--------|
| 安装 | 需要单独安装配置 | 零安装，一个文件 |
| 维护 | 需要管理进程、备份 | 零维护 |
| 并发 | 支持高并发 | 单用户桌面应用完全够用 |
| 数据量 | PB 级 | GB 级足够（个人知识库） |
| 打包 | 无法嵌入 .exe | 天然嵌入 |

### 为什么用 diskcache 而不是 Redis？

| 对比 | Redis | diskcache |
|------|-------|-----------|
| 安装 | 需要单独安装 Redis 服务 | 零安装，基于 SQLite |
| 持久化 | 需配置 RDB/AOF | 默认持久化到磁盘 |
| 功能 | 功能强大 | 单用户场景的缓存/锁/队列完全够用 |
| 打包 | 无法嵌入 .exe | 纯 Python，天然嵌入 PyInstaller |

## 四、核心模块详细设计

### 4.1 知识库模块 — 文档解析、切片、向量化

#### 文档解析：工厂模式 + 多格式支持

| 文件类型 | 解析方案 | 说明 |
|---------|---------|------|
| PDF | `pdfplumber` + `unstructured` | pdfplumber 提取表格，unstructured 提取文本 |
| Word (.docx) | `python-docx` | 原生解析，保留段落结构 |
| Excel (.xlsx) | `openpyxl` + `pandas` | 表格数据转 Markdown 文本 |
| TXT/Markdown | 原生读取 | 直接分片 |

#### 文本切片：多粒度自适应

| 策略 | 适用场景 | 参数 |
|------|---------|------|
| 固定大小滑动窗口 | 通用文本 | chunk_size=500, overlap=50 |
| 语义分块 | 段落自然的文档 | 按段落/标题边界切分 |
| 表格分块 | Excel 文档 | 每行一个 chunk，附带表头 |

- 使用 LangChain `RecursiveCharacterTextSplitter` + `jieba` 分词避免中文词语截断
- 每个 chunk 携带元数据：来源文档 ID、页码、Sheet 名

#### 向量化

- 默认 `BAAI/bge-large-zh-v1.5`（本地运行，1024 维）
- 抽象 EmbeddingService 接口，支持切换云端 API

#### 文档解析并发锁

文档解析是重任务（PDF 解析、切片、向量化），使用 diskcache 实现分布式锁防止并发导致资源耗尽或重复处理。

```python
class DocumentProcessingLock:
    """文档解析锁 —— 防止同一文档被并发重复处理"""
    
    def __init__(self, cache):
        self.cache = cache  # diskcache 实例
    
    async def acquire(self, document_id: str, ttl: int = 3600) -> bool:
        """
        获取文档处理锁
        - 同一文档同一时间只能被一个 worker 处理
        - TTL = 1 小时，防止死锁
        """
        lock_key = f"doc_lock:{document_id}"
        return self.cache.add(lock_key, "processing", expire=ttl)
    
    async def release(self, document_id: str):
        """释放锁"""
        self.cache.delete(f"doc_lock:{document_id}")
    
    async def is_processing(self, document_id: str) -> bool:
        """检查文档是否正在处理中"""
        return self.cache.get(f"doc_lock:{document_id}") is not None


# 使用示例
async def process_document(document_id: str):
    lock = DocumentProcessingLock(cache_client)
    
    # 获取锁，如果已有 worker 在处理则跳过
    if not await lock.acquire(document_id):
        logger.info(f"文档 {document_id} 正在被其他 worker 处理，跳过")
        return
    
    try:
        # 1. 解析文档
        # 2. 切片
        # 3. 向量化
        # 4. 写入向量库
        # 5. 更新文档状态为 completed
        pass
    finally:
        await lock.release(document_id)
```

**锁策略：**

| 场景 | 锁类型 | 说明 |
|------|--------|------|
| 文档解析 | 文档级锁 | 同一文档不并发处理 |
| 知识库重建 | 知识库级锁 | 整个知识库重建时加锁，防止同时写入 |
| 聊天记录导入 | 文件级锁 | 同一文件不重复导入 |

#### 文档解析降级策略

解析重任务如果 CPU/内存扛不住，自动降级：

```python
class DocumentParserDegradation:
    """文档解析降级 —— 资源不够时自动简化"""
    
    async def parse_with_degradation(self, file_path: str, file_type: str) -> ParseResult:
        """解析文档，资源不足时自动降级"""
        
        try:
            # 尝试完整解析（表格提取 + 段落提取 + 结构保留）
            return await self._full_parse(file_path, file_type)
            
        except MemoryError:
            logger.warning("内存不足，降级为纯文本提取")
            # 降级：只提取纯文本，跳过表格解析
            return await self._text_only_parse(file_path, file_type)
            
        except TimeoutError:
            logger.warning("解析超时，降级为分页解析")
            # 降级：分页解析，每页单独处理
            return await self._paginated_parse(file_path, file_type, page_size=5)
    
    async def _full_parse(self, file_path, file_type):
        """完整解析"""
        ...
    
    async def _text_only_parse(self, file_path, file_type):
        """纯文本降级解析 —— 放弃表格、结构，只提取文字"""
        ...
    
    async def _paginated_parse(self, file_path, file_type, page_size):
        """分页降级解析 —— 每次只处理 N 页，分批向量化"""
        ...
```

**降级触发条件：**

| 条件 | 降级行为 |
|------|---------|
| 内存 > 80% | 切换为纯文本提取，跳过表格 |
| 单文件 > 100MB | 分页解析，每 5 页一批 |
| 解析超时 > 5 分钟 | 跳过当前页，标记异常，继续下一页 |
| 连续失败 3 次 | 暂停解析，通知用户手动处理 |

### 4.1.5 聊天记录持续学习（核心差异化能力）

这是智答引擎区别于普通文档问答的关键——**从指定用户的聊天中持续学习**。

#### 核心学习策略：先识别问题，再学习回答

群里的指定用户也会说笑闲聊，所以不能无差别学习所有消息。策略很简单：

```
指定用户的消息流
      │
      ▼
┌──────────────┐
│ 1. 问题识别   │  ← 判断这条消息是不是一个"问题"
│  (Question   │     包含问号？疑问词？求助意图？
│   Detector)  │     不是问题 → 跳过（说笑、闲聊不学）
└──────┬───────┘
       │ 是问题
       ▼
┌──────────────┐
│ 2. 等待回答   │  ← 等待该用户的下一条消息（或群内下一条消息）
│  (Answer     │     作为该问题的回答
│   Waiter)    │
└──────┬───────┘
       │ 获取到回答
       ▼
┌──────────────┐
│ 3. 质量过滤   │  ← 回答太短（< 5字）？纯表情？重复内容？
│  (Quality    │     不合格 → 不学
│   Filter)    │
```

```python
class QuestionDetector:
    """问题识别器 —— 判断一条消息是否是问题"""
    
    # 强疑问特征（高置信度）
    STRONG_PATTERNS = [
        r'.*[\?？].*',           # 包含问号
        r'.*请问.*',             # 请问
        r'.*怎么.*',             # 怎么
        r'.*如何.*',             # 如何
        r'.*什么(是|叫|意思).*',  # 什么是/什么叫/什么意思
        r'.*为(什么|啥|何).*',    # 为什么/为啥/为何
        r'.*有没有.*',           # 有没有
        r'.*能不能.*',           # 能不能
        r'.*可以吗.*',           # 可以吗
        r'.*行不行.*',           # 行不行
    ]
    
    # 弱疑问特征（需要 LLM 二次确认）
    WEAK_PATTERNS = [
        r'.*推荐.*',             # 可能是在问推荐
        r'.*区别.*',             # 可能在问区别
        r'.*哪个.*',             # 可能在问选择
    ]
    
    async def is_question(self, message: str) -> bool:
        """判断消息是否为问题"""
        # 1. 规则快速匹配
        for pattern in self.STRONG_PATTERNS:
            if re.match(pattern, message):
                return True
        
        # 2. 弱特征 → LLM 判断
        for pattern in self.WEAK_PATTERNS:
            if re.match(pattern, message):
                return await self._llm_check(message)
        
        # 3. 不是问题（说笑、闲聊、感叹）
        return False
```

### 4.2 问答引擎 — 混合检索 + 图检索 + 重排序 + Prompt 工程

#### 三路检索架构（核心）

```
用户查询
    │
    ├──▶ 向量检索 (语义相似度) ──────────▶ Top-20
    │
    ├──▶ BM25 检索 (关键词匹配) ─────────▶ Top-20
    │
    └──▶ 图检索 (知识图谱关联) ──────────▶ 关联实体
              │
              ▼
         RRF 融合 (Reciprocal Rank Fusion, k=60)
              │
              ▼
         Top-10 候选片段 + 图关联上下文
              │
              ▼
         Cross-Encoder 重排序 (BGE-Reranker)
              │
              ▼
         Top-3~5 最终上下文 → 组装 Prompt → LLM 生成
```

#### 4.2.1 图检索（Graph RAG）—— 为什么需要？

传统 RAG 只做向量相似度匹配，存在的问题：

| 问题 | 例子 | 图检索如何解决 |
|------|------|---------------|
| **碎片化** | 知识库有"A 商品退货流程"和"B 商品退货流程"，但两段文档分散在不同切片 | 图检索通过"退货流程"实体关联所有相关节点 |
| **跳步推理** | 用户问"XX 问题怎么解决"，需要先知道 XX 属于哪个分类，再找对应方案 | 图检索沿 `问题 → 分类 → 解决方案` 路径遍历 |
| **多跳关联** | "A 功能和 B 功能有什么区别"——需要同时检索 A 和 B 的知识 | 图检索从两个实体出发，汇聚到对比节点 |
| **社区发现** | 聊天记录中同一主题的讨论被时间冲散 | 图检索通过社区发现聚合相关讨论 |

```python
class GraphBuilder:
    """从知识库自动构建知识图谱"""
    
    async def build_from_chunks(self, chunks: List[Chunk]) -> nx.Graph:
        """从切片构建图"""
        G = nx.Graph()
        
        for chunk in chunks:
            # 1. 实体提取：用 LLM 提取关键实体
            entities = await self._extract_entities(chunk.content)
            
            # 2. 创建节点
            for entity in entities:
                G.add_node(entity.name, type=entity.type, chunk_id=chunk.id)
            
            # 3. 创建边（实体之间的关系）
            for rel in entities.relations:
                G.add_edge(rel.source, rel.target, relation=rel.type)
        
        return G

class GraphRetriever:
    """图检索器"""
    
    async def retrieve(self, query: str, G: nx.Graph, top_k: int = 5) -> List[str]:
        """图检索"""
        # 1. 从查询中提取实体
        query_entities = await self._extract_entities(query)
        
        # 2. 在图找到对应节点
        matched_nodes = []
        for entity in query_entities:
            for node in G.nodes:
                if self._similar(entity.name, node):
                    matched_nodes.append(node)
        
        # 3. 获取邻居节点（1~2 跳）
        context_chunks = set()
        for node in matched_nodes:
            neighbors = nx.ego_graph(G, node, radius=2)
            for n in neighbors.nodes:
                context_chunks.add(G.nodes[n].get('chunk_id'))
        
        # 4. 返回关联的切片内容
        return list(context_chunks)[:top_k]
```

#### 4.2.2 向量检索精度优化：反馈 + 合并 + 去重 + 降噪

向量检索精度不是一蹴而就的，需要持续优化：

```python
class VectorOptimizer:
    """向量检索精度优化器 —— 四步提升检索质量"""
    
    # ── 1. 用户反馈优化（实时生效）──
    async def feedback_boost(self, chunk_id: str, rating: int):
        """
        用户点赞/点踩 → 调整检索权重
        - 点赞：该 chunk 在后续检索中加权 1.2x
        - 点踩：该 chunk 在后续检索中降权 0.8x
        """
        if rating > 0:  # 点赞
            await self._boost_chunk(chunk_id, factor=1.2)
        else:           # 点踩
            await self._boost_chunk(chunk_id, factor=0.8)
    
    # ── 2. 向量块合并（定时任务）──
    async def merge_similar_chunks(self, threshold: float = 0.92):
        """
        合并高度相似的向量块
        - 相似度 > 0.92 的两个 chunk → 合并为一个
        - 减少冗余，提高检索效率
        """
        chunks = await self._get_all_chunks()
        merged = []
        skip_ids = set()
        
        for i, chunk_a in enumerate(chunks):
            if chunk_a.id in skip_ids:
                continue
                
            for chunk_b in chunks[i+1:]:
                if chunk_b.id in skip_ids:
                    continue
                    
                similarity = self._cosine_sim(chunk_a.vector, chunk_b.vector)
                if similarity > threshold:
                    # 合并：保留更长的那个，删除短的
                    if len(chunk_a.content) >= len(chunk_b.content):
                        skip_ids.add(chunk_b.id)
                    else:
                        skip_ids.add(chunk_a.id)
                        break
            
            if chunk_a.id not in skip_ids:
                merged.append(chunk_a)
        
        # 删除被合并的 chunk
        await self._delete_chunks(skip_ids)
        return merged
    
    # ── 3. 向量去重（定时任务）──
    async def deduplicate_chunks(self, threshold: float = 0.98):
        """
        去除完全重复的向量块
        - 相似度 > 0.98 → 视为重复，只保留一个
        - 常见于：聊天记录中同一问题被多次回答
        """
        return await self.merge_similar_chunks(threshold=threshold)
    
    # ── 4. 降噪过滤（定时任务）──
    async def filter_noise(self):
        """
        过滤低质量向量块
        - 内容太短（< 10 字）
        - 纯数字/纯符号
        - 与知识库主题无关的闲聊
        """
        chunks = await self._get_all_chunks()
        noise_ids = []
        
        for chunk in chunks:
            if len(chunk.content) < 10:
                noise_ids.append(chunk.id)
            elif self._is_pure_noise(chunk.content):
                noise_ids.append(chunk.id)
            elif await self._is_off_topic(chunk.content, chunk.kb_id):
                noise_ids.append(chunk.id)
        
        await self._delete_chunks(noise_ids)
        return len(noise_ids)
    
    def _is_pure_noise(self, text: str) -> bool:
        """判断是否为纯噪音"""
        # 纯数字、纯符号、纯表情
        cleaned = re.sub(r'[\d\s\W]', '', text)
        return len(cleaned) < 3


# 定时优化任务
async def optimize_vectors(kb_id: str):
    optimizer = VectorOptimizer()
    
    # 1. 合并相似块
    merged = await optimizer.merge_similar_chunks()
    logger.info(f"合并了 {merged} 个相似块")
    
    # 2. 去重
    deduped = await optimizer.deduplicate_chunks()
    logger.info(f"去重了 {deduped} 个重复块")
    
    # 3. 降噪
    noise_count = await optimizer.filter_noise()
    logger.info(f"过滤了 {noise_count} 个噪音块")
```

**优化触发时机：**

| 触发方式 | 频率 | 说明 |
|---------|------|------|
| 用户反馈 | 实时 | 每次点赞/点踩立即调整权重 |
| 定时合并 | 每天凌晨 | 自动合并相似向量、去重 |
| 手动触发 | 用户操作 | 管理后台点击"优化知识库" |
| 新数据入库后 | 事件触发 | 新导入聊天记录后自动降噪 |

#### 4.2.3 三路检索方案选型

| 方案 | 优点 | 缺点 | 适合 |
|------|------|------|------|
| **手搓** | 完全可控，无依赖 | 开发量大，中文分词复杂 | ❌ 重复造轮子 |
| **VikingDB** | 混合检索内置 | 云服务，需网络，有成本，违背本地部署 | ❌ |
| **Mem0** | 开源，AI 记忆设计，图记忆 | 社区在成长，中文优化待验证 | ✅ 聊天记忆辅助 |
| **LangChain + LlamaIndex** | 混合检索内置，图 RAG 支持 | 有点重但可裁剪 | ✅ 最佳选择 |

**推荐方案：LangChain + LlamaIndex 为主，Mem0 辅助聊天记忆**

```python
# backend/app/services/llm/gateway.py

class LLMGateway:
    """LLM 统一网关 —— 从数据库读取配置，支持厂商模板和自定义模型"""
    
    def __init__(self, db_session):
        self.db = db_session
        self._model_cache: Dict[str, LLMConfigModel] = {}
    
    async def get_llm(self, config_type: str = "primary") -> ChatOpenAI:
        """
        获取 LLM 实例
        - config_type: "primary" 主模型 / "fallback" 降级模型
        """
        # 从数据库读取配置
        config = await self._get_config(config_type)
        if not config:
            raise ValueError(f"未配置 {config_type} 模型，请在设置页配置")
        
        return ChatOpenAI(
            model=config.model_name,
            base_url=config.base_url,
            api_key=config.api_key or "ollama",  # Ollama 不需要真实 key
            streaming=True,
            **config.extra_params or {},
        )
    
    async def _get_config(self, config_type: str) -> Optional[LLMConfigModel]:
        """从数据库获取配置"""
        if config_type in self._model_cache:
            return self._model_cache[config_type]
        
        config = await self.db.query(LLMConfigModel).filter(
            LLMConfigModel.config_type == config_type,
            LLMConfigModel.is_active == True,
        ).first()
        
        if config:
            self._model_cache[config_type] = config
        return config
    
    async def list_providers(self) -> List[ProviderTemplateResponse]:
        """列出所有可用厂商模板（设置页展示）"""
        return [
            ProviderTemplateResponse(
                provider_id=t.provider_id,
                provider_name=t.provider_name,
                base_url=t.base_url,
                default_model=t.default_model,
                available_models=t.available_models,
                requires_api_key=t.requires_api_key,
                api_key_placeholder=t.api_key_placeholder,
                is_local=t.is_local,
                icon=t.icon,
                description=t.description,
            )
            for t in BUILTIN_PROVIDER_TEMPLATES
        ]
    
    async def save_config(self, config: LLMConfigCreate) -> LLMConfigModel:
        """保存 LLM 配置"""
        # 加密 API Key
        if config.api_key:
            config.api_key = self._encrypt_api_key(config.api_key)
        
        model = LLMConfigModel(
            id=f"{config.config_type}_{datetime.utcnow().timestamp()}",
            **config.model_dump(),
        )
        self.db.add(model)
        await self.db.commit()
        
        # 清除缓存
        self._model_cache.pop(config.config_type, None)
        return model
    
    async def test_connection(self, config: LLMConfigCreate) -> dict:
        """
        测试连接 —— 发送测试消息验证连通性
        不消耗 Token，只验证 API Key 和 Base URL 是否正确
        """
        try:
            llm = ChatOpenAI(
                model=config.model_name,
                base_url=config.base_url,
                api_key=config.api_key or "ollama",
                max_tokens=1,  # 只生成 1 个 token，最小消耗
            )
            await llm.ainvoke("ping")
            return {"success": True, "message": "连接成功"}
        except Exception as e:
            return {"success": False, "message": str(e)}
    
    def _encrypt_api_key(self, api_key: str) -> str:
        """加密 API Key（本地存储，简单编码即可）"""
        import base64
        return base64.b64encode(api_key.encode()).decode()
    
    def _decrypt_api_key(self, encrypted: str) -> str:
        """解密 API Key"""
        import base64
        return base64.b64decode(encrypted.encode()).decode()
```

### 4.4 缓存与降级 — Token 成本控制 + 可用性保障

#### 三层缓存架构

```
L1: 精确匹配缓存 (diskcache, TTL=24h)
    └─ 完全相同的 question → 直接返回缓存答案

L2: 语义相似缓存 (diskcache + 向量, TTL=7d)
    └─ 相似度 > 0.95 的问题 → 返回缓存答案

L3: 幂等控制 (diskcache, TTL=5min)
    └─ 基于 question + channel_user_id 的 MD5 去重
    └─ 短时间内相同问题只处理一次
```

**Token 节省估算：综合节省约 30-45%**

#### Single-Flight 幂等合并

Single-Flight 是比普通幂等更进一步的模式——**相同请求并发时，只执行一次，所有等待者共享结果**。

```python
import asyncio
from typing import Dict, Set

class SingleFlight:
    """Single-Flight 模式 —— 相同请求合并为一次执行，结果广播给所有等待者"""
    
    def __init__(self):
        self._in_flight: Dict[str, asyncio.Event] = {}
        self._results: Dict[str, str] = {}
        self._waiters: Dict[str, int] = {}
    
    async def do(self, key: str, fn, *args, **kwargs) -> str:
        """
        执行 fn(key, *args, **kwargs)，如果 key 相同：
        - 第一个请求：执行 fn
        - 后续请求：等待第一个请求的结果，共享返回
        """
        # 如果已有结果，直接返回
        if key in self._results:
            return self._results[key]
        
        # 如果正在执行中，等待结果
        if key in self._in_flight:
            self._waiters[key] += 1
            await self._in_flight[key].wait()
            return self._results[key]
        
        # 第一个请求：执行并广播结果
        self._in_flight[key] = asyncio.Event()
        self._waiters[key] = 1
        
        try:
            result = await fn(*args, **kwargs)
            self._results[key] = result
            return result
        finally:
            # 通知所有等待者
            self._in_flight[key].set()
            del self._in_flight[key]
            
            # 结果保留 TTL 后清除
            asyncio.create_task(self._expire(key, ttl=300))
    
    async def _expire(self, key: str, ttl: int):
        """TTL 过期清除"""
        await asyncio.sleep(ttl)
        self._results.pop(key, None)
        self._waiters.pop(key, None)


# 使用示例（问答 API 中）
single_flight = SingleFlight()

@router.post("/api/v1/chat/ask")
async def ask_question(request: QuestionRequest):
    # 生成 single-flight key：问题 + 知识库 ID 的哈希
    sf_key = hashlib.md5(
        f"{request.question}:{request.knowledge_base_id}".encode()
    ).hexdigest()
    
    # Single-Flight：相同问题并发只执行一次 LLM 调用
    answer = await single_flight.do(
        key=sf_key,
        fn=qa_service.answer,
        question=request.question,
        kb_id=request.knowledge_base_id,
    )
    
    return {"answer": answer}
```

**Single-Flight 效果：**

```
时间线：群聊中 3 个人同时 @机器人 问 "怎么退货？"

没有 Single-Flight:
  T0: 请求1 → LLM调用1 → Token消耗
  T0: 请求2 → LLM调用2 → Token消耗 (重复!)
  T0: 请求3 → LLM调用3 → Token消耗 (重复!)
  总计: 3次LLM调用, 3倍Token

有 Single-Flight:
  T0: 请求1 → LLM调用1 → Token消耗
  T0: 请求2 → 等待请求1 → 共享结果
  T0: 请求3 → 等待请求1 → 共享结果
  总计: 1次LLM调用, 1倍Token, 节省 67%
```

### 4.5 限流与安全

#### 刷屏限流策略

群聊场景最容易出现刷屏，需要多层限流：

```python
class RateLimiter:
    """多层限流 —— 令牌桶 + 滑动窗口"""
    
    def __init__(self, cache=None):
        self.cache = cache  # diskcache 实例
    
    # ── 第一层：令牌桶（平滑限流）──
    async def check_token_bucket(self, key: str, rate: int, burst: int) -> bool:
        """
        令牌桶限流
        - rate: 每秒允许的请求数
        - burst: 突发容量（桶大小）
        """
        now = time.time()
        bucket = await self._get_bucket(key)
        
        # 补充令牌
        elapsed = now - bucket["last_refill"]
        bucket["tokens"] = min(burst, bucket["tokens"] + elapsed * rate)
        bucket["last_refill"] = now
        
        if bucket["tokens"] >= 1:
            bucket["tokens"] -= 1
            await self._save_bucket(key, bucket)
            return True  # 放行
        
        return False  # 限流
    
    # ── 第二层：滑动窗口（防突发）──
    async def check_sliding_window(self, key: str, max_req: int, window: int) -> bool:
        """
        滑动窗口限流
        - max_req: 时间窗口内最大请求数
        - window: 时间窗口（秒）
        """
        now = time.time()
        cutoff = now - window
        
        # 移除过期记录
        await self._remove_expired(key, cutoff)
        
        # 当前窗口内请求数
        count = await self._count_in_window(key, cutoff)
        
        if count < max_req:
            await self._add_request(key, now)
            return True
        
        return False

    """群聊限流配置"""
    
    # 第一层：令牌桶 —— 每秒最多回复 1 条
    REPLY_TOKEN_RATE = 1       # 每秒 1 个令牌
    REPLY_TOKEN_BURST = 3      # 桶容量 3（允许短时突发 3 条）
    
    # 第二层：滑动窗口 —— 每分钟最多 10 条
    REPLY_MINUTE_MAX = 10      # 每分钟最多 10 条
    REPLY_MINUTE_WINDOW = 60   # 60 秒窗口
    
    # 第三层：冷却期 —— 10 秒内相同问题不重复回复
    QUESTION_COOLDOWN = 10     # 相同问题冷却 10 秒
    
    # 第四层：静默时段 —— 凌晨 2:00-6:00 不回复
    SILENT_START = 2           # 静默开始时间
    SILENT_END = 6             # 静默结束时间


async def group_message_handler(group_id: str, user_id: str, message: str):
    """群聊消息处理 —— 带多层限流"""
    limiter = RateLimiter()
    config = GroupRateLimitConfig()
    
    # 0. 静默时段检查
    hour = datetime.now().hour
    if config.SILENT_START <= hour < config.SILENT_END:
        return  # 静默时段，不回复
    
    # 1. 第一层：令牌桶
    if not await limiter.check_token_bucket(
        f"token:{group_id}", 
        config.REPLY_TOKEN_RATE, 
        config.REPLY_TOKEN_BURST
    ):
        logger.info(f"群 {group_id} 令牌桶限流，跳过")
        return
    
    # 2. 第二层：滑动窗口
    if not await limiter.check_sliding_window(
        f"window:{group_id}",
        config.REPLY_MINUTE_MAX,
        config.REPLY_MINUTE_WINDOW
    ):
        logger.info(f"群 {group_id} 滑动窗口限流，跳过")
        return
    
    # 3. 第三层：问题冷却
    question_hash = hashlib.md5(message.encode()).hexdigest()
    if not await limiter.check_sliding_window(
        f"cooldown:{group_id}:{question_hash}",
        1,  # 冷却期内只允许 1 次
        config.QUESTION_COOLDOWN
    ):
        logger.info(f"群 {group_id} 相同问题冷却中，跳过")
        return
    
    # 4. 通过所有限流，正常处理
    await process_and_reply(group_id, user_id, message)
```

**限流效果：**

```
同一群聊，10 个人同时 @机器人问不同问题：
  → 令牌桶允许突发的 3 条立即回复
  → 滑动窗口确保每分钟不超过 10 条
  → 其余排队或丢弃

同一群聊，3 个人同时问"怎么退货？"：
  → 问题冷却：10 秒内只回复一次
  → 其余 2 人如果开了 Single-Flight，共享结果
  → 如果没开，冷却期内不回复（避免刷屏）
```

#### 启动流程

```python
# main.py —— 应用入口
import uvicorn
import webview
import threading
from pathlib import Path

class ZhidaEngineAPI:
    """暴露给前端 JS 的 Python API（PyWebView 双向通信）"""
    
    def __init__(self, window):
        self.window = window
    
    def open_external_url(self, url: str):
        """在外部浏览器打开链接"""
        import webbrowser
        webbrowser.open(url)
    
    def get_app_version(self) -> str:
        return "1.0.0"
    
    def minimize_to_tray(self):
        """最小化到系统托盘"""
        self.window.hide()
        create_tray_icon(self.window)

def main():
    """应用启动入口"""
    # 1. 确保数据目录存在
    data_dir = Path.home() / "AppData" / "Local" / "ZhidaEngine"
    data_dir.mkdir(parents=True, exist_ok=True)
    
    # 2. 初始化数据库（SQLite，自动建表）
    init_database(data_dir / "zhida.db")
    
    # 3. 初始化缓存（diskcache）
    init_cache(data_dir / "cache.db")
    
    # 4. 启动 FastAPI 服务（后台线程，监听 127.0.0.1:8000）
    server_thread = threading.Thread(
        target=uvicorn.run,
        args=("app:app",),
        kwargs={"host": "127.0.0.1", "port": 8000, "log_level": "info"},
        daemon=True,
    )
    server_thread.start()
    
    # 5. 创建系统托盘图标
    create_tray_icon()
    
    # 6. 创建原生 Windows 窗口，嵌入 React 前端
    #    PyWebView 使用 Windows 内置 WebView2，无需额外安装
    api = ZhidaEngineAPI(None)
    window = webview.create_window(
        title="智答引擎",
        url="http://127.0.0.1:8000",  # React 前端由 FastAPI serve
        js_api=api,                    # Python ↔ JS 双向通信
        width=1200,
        height=800,
        min_size=(900, 600),
        confirm_close=True,            # 关闭时确认（最小化到托盘 or 退出）
    )
    api.window = window
    
    # 7. 启动窗口（阻塞，直到窗口关闭）
    webview.start(debug=False)

if __name__ == "__main__":
    main()
```

**PyWebView 的优势：**

| 对比 | 浏览器 | PyWebView | Electron |
|------|--------|-----------|----------|
| 用户看到 | 浏览器标签页，有地址栏 | 原生 Windows 窗口，无地址栏 | 原生窗口 |
| 安装包体积 | ~500MB | ~500MB | ~700MB+ |
| 额外依赖 | 无 | WebView2（Win10/11 已内置） | Chromium 内嵌 |
| 前端代码 | 不变 | 不变 | 不变 |
| 窗口控制 | 浏览器控制 | 应用控制（最小化到托盘等） | 应用控制 |
| Python 通信 | HTTP API | HTTP API + JS→Python 直接调用 | 需 IPC 桥接 |

**核心：React 前端代码完全不用改。** 只是从"浏览器打开 localhost"变成了"PyWebView 原生窗口打开 localhost"，前端开发体验和之前一模一样。

## 七、关键设计决策

| 决策点 | 选择 | 核心理由 |
|--------|------|---------|
| 后端语言 | Python | AI 生态唯一选择，LangChain/LlamaIndex 不可替代 |
| 架构模式 | 单进程桌面应用 | 一切嵌入式，零外部依赖，双击就能用 |
| 数据库 | SQLite（嵌入式） | 零安装、零维护，单用户场景完全够用 |
| 缓存 | diskcache（SQLite 后端） | 替代 Redis，嵌入式，默认持久化 |
| 向量数据库 | ChromaDB（嵌入式模式） | Python 原生，零依赖，数据随应用存储 |
| LLM 方案 | 厂商模板自动填充 + 全自定义 | 用户选择厂商即自动填充，也支持完全手动配置 |
| LLM 接入 | LiteLLM + Ollama 本地模型 | 云端 API 为主，本地模型降级兜底 |
| 微信群接入 | Wechaty + 普通微信个人号 | 个人用户无需企业认证 |
| QQ 群接入 | NapCatQQ + OneBot v11 | 基于 NTQQ，稳定可靠，协议标准 |
| 学习策略 | 先识别问题 → 再学习回答 | 过滤说笑闲聊，精准学习 |
| 前端框架 | React + Ant Design，静态文件 | 构建后由 FastAPI 直接 serve，无需 Node 运行时 |
| 桌面窗口 | PyWebView（Windows WebView2） | 原生窗口体验，无浏览器 UI |
| 部署方式 | Windows .exe 安装包 | 双击安装，桌面快捷方式，开箱即用 |
| 打包工具 | PyInstaller | 将 Python + 所有依赖 + 前端打包为单个 .exe |
| 安装包制作 | NSIS / Inno Setup | 标准 Windows 安装向导，创建快捷方式、卸载入口 |

## 八、风险与缓解

| 风险 | 缓解方案 |
|------|---------|
| LLM API 不稳定 | 多模型自动切换（DeepSeek V4 → 通义千问 Qwen3.7 → 本地 Ollama） |
| Wechaty 风控 | 使用小号/专用号，控制消息频率，仅服务白名单群 |
| 问题识别不准 | 规则 + LLM 双引擎判断，持续优化识别正则 |
| 知识库膨胀 | 定时合并、去重、降噪，用户可手动清理 |
| Token 成本过高 | 三层缓存 + Single-Flight 合并，估计节省 30-45% |
| 解析大文件 OOM | 四级降级策略（纯文本 → 分页 → 跳过 → 暂停） |
| 群聊刷屏 | 四层限流（令牌桶 + 滑动窗口 + 问题冷却 + 静默时段） |
| 数据泄露 | 全链路本地部署，API Key 加密存储，Ollama 完全离线 |
| 单用户性能瓶颈 | SQLite + diskcache 在单用户场景下性能充足 |

## 九、验证方式

### 功能验证

| 模块 | 验证方法 | 通过标准 |
|------|---------|---------|
| 文档解析 | 上传 PDF/Word/Excel 各 1 个 | 文件解析成功，显示切片数 > 0 |
| 聊天记录解析 | 导入微信/QQ 导出文件 | 消息列表正确展示，发送者/时间/内容匹配 |
| 问题识别 | 输入"怎么退货？"和"今天天气真好" | 前者识别为问题，后者忽略 |
| 向量检索 | 在问答测试页提问 | 返回相关文档片段，相似度 > 0.6 |
| 混合检索 | 提问包含关键词"退货" | 向量 + BM25 结果都包含在候选中 |
| LLM 回答 | 提问知识库中存在的问题 | 回答准确，引用来源，无幻觉 |
| 厂商模板 | 选择"DeepSeek" → 输入 API Key → 测试连接 | 自动填充 Base URL/模型列表，连接成功 |
| 自定义模型 | 选择"自定义" → 手动填写所有字段 | 所有字段可编辑，保存后可使用 |
| 降级模型 | 断开 DeepSeek API，验证自动切换 Ollama | 自动切换到降级模型，不停机 |
| 缓存命中 | 连续两次问相同问题 | 第二次直接从缓存返回，Token 消耗为 0 |
| Single-Flight | 并发 3 个相同问题 | 只执行 1 次 LLM 调用，3 个请求都得到结果 |
| 限流 | 10 秒内发 10 条群消息 | 回复不超过 3 条（令牌桶 + 滑动窗口） |
| 自动@求助 | 提问知识库中不存在的"复杂问题" | 自动 @指定用户，用户回复后自动学习 |
| 消息来源展示 | 开启后提问 | 回答底部显示"📌 来自 xxx 的聊天记录" |
| Agent 管理 | 创建 2 个 Agent，分别绑定不同群 | 仪表盘正确显示各 Agent 状态和统计 |
